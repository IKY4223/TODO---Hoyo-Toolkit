# Этап 20. Genshin: урон по талантам, артефакты, удача

План для сессии, которая будет строить этап. Написан в ноябре 2026 после PR #21.
Сначала прочитай `CLAUDE.md` целиком: его правила выше этого файла. Где этот файл расходится
с кодом, прав код: проверь и скажи владельцу.

## Как работать

- **Модель и усилие.** Opus 5.5, уровень усилий `high`. Часть B2 (сравнение артефактов) —
  `xhigh`: там легко ошибиться в пересчёте характеристик. Fable не нужен.
- **Два PR, не один.** PR A: части A1–A4. PR B: части B1–B3. Каждый PR проходит `./check.sh`,
  владелец мержит его, потом ветка подтягивается к `main`.
- **Порядок внутри части:** падающий тест, код, `./check.sh`, скриншоты владельцу (компьютер
  1440×900 и телефон 360px, обе темы, русский язык).
- **Форматтера для фронтенда в проекте нет.** Не запускай `prettier`: он перепишет файлы
  целиком. Пиши в стиле соседнего кода: без точек с запятой, одинарные кавычки, строка до 100
  знаков. Линтер — `oxlint` (`npm run lint`), он запрещает `await` в цикле.
- **Тесты не ходят в сеть.** Данные игры лежат в сгенерированных файлах репозитория; сеть
  нужна только скрипту синхронизации, который запускают руками.
- **Интерфейс на двух языках.** Каждая новая строка — ключ в `frontend/src/i18n.ts` (объект
  `RU`, английский текст — ключ, русский — значение).

## PR A. Урон по талантам

**Сделано (ноябрь 2026).** Отличия от плана: подписи ударов лежат в «средних» текстовых картах
(`TextMap_MediumEN.json`, `TextMap_MediumRU_0/1.json`), русские тоже есть. Стат каждой части
удара берётся из самой подписи (`ATK`, `Max HP`, `DEF`, `Elemental Mastery`), удар с двумя
статами отправляется в API двумя частями (`scalings`). Повторы (`×3`) и части через `+`
сложены в один множитель. Выгрузка Dimbreath обновлялась в июне 2026: у новейших персонажей
таблиц пока нет.

### A1. Данные талантов

- Расширь `backend/scripts/sync_gamedata.py`: он скачивает `ProudSkillExcelConfigData.json` и
  текстовые карты и пишет новый файл `backend/app/showcase/talents.json`.
- Форма файла: `{ "<id группы>": { "rows": [ { "label": {"en": "...", "ru": "..."},
  "params": [номера параметров с нуля], "format": "F1P" } ], "levels": { "1": [числа], ... } } }`.
  Бери только группы, которые встречаются в `gamedata.json` → `characters[*].talents`.
- Оставляй только строки урона: формат с `P` (процент). Строки с секундами, выносливостью и
  энергией (`F1`, `I`, без `P`) пропускай. Строку с двумя параметрами через `+`
  (`{param5:F1P}+{param6:F1P}`) храни как один удар с двумя множителями: в API уйдёт их сумма.
  Строку через `/` (низкий и высокий удар в падении) раздели на две.
- Файл генерируемый: добавь его в правило `CLAUDE.md` про файлы, которые не правят руками.
- Чтение: функция в `backend/app/showcase/gamedata.py` рядом с существующей загрузкой.
- Тесты: `backend/tests/test_showcase_gamedata.py` (новый). Проверь на готовом файле: у группы
  231 на уровне 1 первый множитель 0.457253; у каждого персонажа из `gamedata.json` три группы
  есть в `talents.json`.

### A2. API: удары персонажа

- В `backend/app/showcase/models.py` добавь к `Character` поле с ударами: для каждого из трёх
  талантов — название строки и множитель на уровне персонажа. Уровень бери из
  `Character.talents`. Уровни выше 10 (с созвездиями до 13, у обычной атаки до 11) в данных
  есть до 15: если уровня нет, строка не попадает в список.
- Заполняй в `backend/app/showcase/enka.py`, там же, где собирается `Character`.
- `./check.sh` перегенерирует `frontend/src/api/schema.d.ts`: закоммить его.
- Тесты: `backend/tests/test_showcase_enka.py` — у персонажа из фикстуры есть удары, множитель
  первого совпадает с `talents.json` для его уровня.

### A3. Калькулятор: выбор удара

- В `frontend/src/damage/DamageCalculator.tsx` поле «Множитель таланта, %» остаётся, над ним
  появляется выпадающий список «Удар»: строки из данных персонажа, сгруппированные по трём
  талантам (`<optgroup>`), и пункт «Свой множитель». Выбор удара подставляет множитель в поле;
  поле можно править руками.
- Стат масштабирования данные не называют. Правило: если подпись содержит `Max HP`, `DEF` или
  `Elemental Mastery` — ставь его, иначе ATK. Это догадка по тексту: пометь
  `shortcut:` и оставь список «Зависит от» доступным для правки.
- Бонус урона по умолчанию: стихия персонажа для навыка и взрыва, физический для обычной
  атаки. Тоже догадка (у катализаторов и наполнений она неверна): `shortcut:` и запись в
  план README.
- На широком экране форма идёт в несколько колонок: см. правило
  `.controls > form:only-child` в `frontend/src/index.css`. Калькулятор стоит внутри
  `<details>` карточки персонажа — проверь на скриншоте, что он не ломает карточку.
- Тесты: `DamageCalculator.test.tsx` (выбор удара подставляет множитель) и сценарий в
  `frontend/e2e/app.spec.ts` рядом с тестом `calculates damage for an imported character`.

### A4. Формула: срез и плоские добавки

В `backend/app/damage/engine.py`, каждая механика отдельным тестом в
`backend/tests/test_damage_engine.py`. Формулы — из KQM Theorycrafting Library, раздел
«Damage Formula»; прочитай страницу, не пиши по памяти, и оставь ссылку в комментарии.

1. **Срез защиты и игнорирование защиты** (два поля, доли): входят в `_defense_factor`.
2. **Срез сопротивления** (доля): вычитается из сопротивления врага до `_resistance_factor`.
3. **Плоская добавка к урону** (число): прибавляется к `стат × множитель` до остальных
   множителей. Этим покрываются Шэньхэ, Юнь Цзинь и подобные.
4. **Aggravate и Spread**: новые значения `Reaction`. Добавка зависит от уровня персонажа и
   мастерства стихий; таблицу базового урона реакций по уровням возьми из игры
   (`ElementCoeffExcelConfigData.json` в том же хранилище Dimbreath) через скрипт
   синхронизации, не из памяти.
5. Трансформирующие реакции (Перегрузка, Сверхпроводник и другие) в этот PR **не входят**:
   это отдельный расчёт без крита. Оставь `shortcut:` и строку в плане README.

Новые поля добавь в `DamageRequest` с границами, границы — в `limits.py`, в форму — поля в
свёрнутом блоке «Дополнительно». Убери из docstring `engine.py` то, что стало сделанным.

### B2. Сравнение артефактов (`xhigh`)

Что делает: для выбранного удара показывает, какой артефакт с витрины игрока в каждом слоте
дал бы этому персонажу больше урона.

- Откуда артефакты: только надетые на персонажей витрины (до 12 персонажей, 5 слотов). Других
  у сайта нет: Enka не отдаёт инвентарь. Скажи это в подсказке на странице.
- Чтобы заменить артефакт, нужны базовые характеристики. Enka отдаёт их в `fightPropMap`
  (id 1, 4, 7 — базовые HP, ATK, DEF). Проверь по фикстуре
  `backend/tests/fixtures/enka_showcase.json` и добавь их в `Character`.
- Пересчёт: итоговые характеристики минус вклад старого артефакта плюс вклад нового. Проценты
  HP, ATK, DEF считаются от базы. Вынеси в чистую функцию в `backend/app/showcase/` и
  проверь тестом: «снять и надеть тот же артефакт» возвращает исходные характеристики.
- **Бонусы наборов не пересчитываются.** Замена ломает или собирает набор, а эффекты наборов
  сайт не знает. Это `shortcut:`, подсказка на странице и строка в плане README.
- API: новый маршрут рядом с `backend/app/damage/api.py`, с ограничением частоты, как у
  соседних. Вход — персонаж, удар, враг, список артефактов-кандидатов. Выход — по слоту:
  артефакт, средний урон, разница с текущим. Границы на длину списков обязательны.
- Интерфейс: блок в карточке персонажа под калькулятором. На широком экране — пять слотов в
  ряд.
- Тесты: движок, API, компонент, сценарий в `app.spec.ts`.

### B3. Доля выигранных 50/50

- Считается на фронтенде в `frontend/src/wishes/history.ts`, в сводке баннера персонажа.
- Победа — 5★ из `featured` баннера, который шёл в момент крутки. Поражение — любой другой
  5★. Крутка сразу после поражения гарантирована и в долю не входит.
- Данные баннеров: сгенерированный файл во фронтенде (скрипт рядом с `sync_gamedata.py`),
  источник — `banners.js` из paimon.moe. Имена там в виде ключей (`venti`): сопоставь с
  именами из истории и проверь тестом на нескольких персонажах с пробелами и апострофами.
- История хранит время крутки в часовом поясе сервера, баннеры с `timezoneDependent` идут по
  местному времени сервера. Используй `serverOffset` из `frontend/src/wishes/uigf.ts`.
- С версии 5.0 Capturing Radiance меняет шанс, но не определение победы: доля считается так же.
- Строка в `BannerCard`: «Выиграно 50/50: N из M». Если баннеров в данных нет для даты
  крутки, эта крутка в долю не входит, и подсказка говорит, сколько таких.
- Star Rail — только если найден источник (см. «Источники данных», пункт 4).
- Тесты: `frontend/src/wishes/history.test.ts` и сценарий импорта в `app.spec.ts`.
